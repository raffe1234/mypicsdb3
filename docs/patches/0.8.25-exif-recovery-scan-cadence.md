# 0.8.25 EXIF recovery and scan cadence

Version 0.8.25 follows two issues reproduced on a real Kodi/NAS installation.

## EXIF fallback hardening

A picture could make ExifRead abort with a `UnicodeDecodeError` while Kodi's own
picture-info dialog still showed camera metadata. Version 0.8.24 added a bounded
core TIFF/EXIF fallback, but diagnostics showed `Core EXIF fallback used: no` on
that real file.

0.8.25 separates metadata-prefix acquisition from image-dimension probing so a
dimension parser failure cannot discard a successfully read EXIF prefix. If the
normal prefix fallback is still empty after ExifRead fails, a fresh Kodi VFS
stream performs a bounded JPEG marker walk. It skips unrelated segments and reads
only an EXIF APP1 payload; MakerNote and free-form UserComment decoding remain
outside the fallback.

Metadata diagnostics now also reports:

- metadata-prefix bytes read;
- whether an embedded EXIF block was found;
- prefix read errors;
- image-dimension probe errors.

No source file is modified and diagnostics remain local to Kodi.

## Restart-stable automatic scan cadence

Before 0.8.25 every add-on service start scheduled an automatic scan after the
configured startup delay, even when the previous complete scan had finished only
recently. Frequent Kodi/add-on restarts could therefore make a 24-hour schedule
look almost continuous.

A complete full scan now stores `last_complete_scan_at` in the existing catalogue
`meta` key/value table. On service startup MyPicsDB calculates the remaining
configured interval from that timestamp. No database schema migration is needed.

A compatible local scan checkpoint intentionally takes precedence: an unfinished
scan resumes after the startup delay instead of waiting another full interval.
When it finally completes, the normal interval starts from that completion time.

Scanning remains serial and all existing scan/checkpoint locks are unchanged.

- Query Model: 1 (unchanged)
- Repository add-on: 0.2.26 (unchanged)
