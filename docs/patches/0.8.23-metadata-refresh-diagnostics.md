# 0.8.23 Metadata refresh and diagnostics

Version 0.8.23 adds an explicit way to re-read metadata for already indexed
still pictures without rebuilding the catalogue or changing source media. It
also adds a privacy-local diagnostic view that compares the currently indexed
canonical values with a fresh extractor result for one selected picture.

## User-facing behaviour

A still-picture context menu now offers:

- **Refresh metadata** — confirms the action, re-reads that file through the
  current EXIF/XMP/IPTC mapping pipeline and transactionally replaces the
  picture's normalized catalogue metadata, tags and search document;
- **Metadata diagnostics** — performs a fresh read without writing and shows
  indexed versus fresh camera/location values plus bounded extractor details
  such as EXIF tag count, raw Make/Model and whether latitude/longitude tags are
  present.

Indexed album/folder context menus also offer **Refresh metadata in this
folder**. It processes only still pictures directly in the selected folder,
serially, with a cancellable progress dialog. Subfolders are deliberately not
included so the action cannot unexpectedly become a catalogue-wide reindex.

## Safety and privacy

Metadata refresh:

- never writes, moves, renames or deletes source media;
- does not traverse source trees and does not perform missing-record cleanup;
- preserves `last_seen_at`, because refresh is not evidence of a source scan;
- uses the current metadata mapping and metadata-index fingerprint;
- updates the normalized search document and the affected folder summary;
- remains serial and performs no parallel SMB/NFS reads;
- coordinates with scans and schema migrations through the dedicated
  `metadata-refresh` catalogue lock;
- can recover a stale process-owned SQLite refresh lock after a crashed Kodi
  process, while shared MariaDB continues to rely on normal lock ownership/TTL;
- never sends metadata or GPS coordinates to a network provider.

Diagnostics are displayed locally in Kodi. Raw metadata and coordinates are not
written to `kodi.log` by the diagnostic action, and stored/fresh coordinates are
shown only while **Store GPS coordinates** is enabled. When GPS storage is off,
the diagnostic can still report whether EXIF GPS tags were detected without
exposing the coordinate pair.

## Why this release exists

Incremental scans intentionally skip metadata reads when file size, mtime and
`metadata_index_hash` still match. That is important for large NAS libraries,
but it can leave an old catalogue row without fields that a newer extractor or
mapping can now understand. Kodi's built-in picture information dialog can also
read source metadata independently of MyPicsDB 3, so it is possible for Kodi to
show Camera Make/Model while the MyPicsDB catalogue still has blank values.

0.8.23 makes that difference inspectable before a user commits to a large
metadata reindex. If **Fresh extraction** finds Make/Model/GPS, **Refresh
metadata** can store those values immediately. If fresh extraction is also
blank while Kodi's own picture dialog shows metadata, the diagnostic identifies
that as an extractor-coverage problem rather than an indexing-age problem.

## Compatibility

- Database schema remains **9**.
- Query Model remains **version 1**.
- No Estuary skin change is required.
- No external geocoding or map provider is added.

## Tests

Coverage includes extractor diagnostics, single-picture refresh, exact-folder
refresh/cancellation, catalogue updates/search tags, scan/refresh/migration lock
conflicts and Kodi context/action smoke tests.
