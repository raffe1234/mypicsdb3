# 0.8.26 Kodi VFS binary metadata reads

Version 0.8.26 fixes the I/O boundary exposed by the 0.8.23-0.8.25 metadata
diagnostics on real SMB-hosted JPEGs. Kodi's built-in picture information could
show Camera make/model while MyPicsDB Fresh extraction returned no EXIF tags and
reported `UnicodeDecodeError` for both ExifRead and metadata-prefix acquisition.

## Root cause

Kodi's Python `xbmcvfs.File.read()` is a text/string read. MyPicsDB's seekable
`KodiFileAdapter` used it for binary JPEG/EXIF streams. A normal JPEG marker begins
with byte `0xff`, which can therefore fail UTF-8 decoding before either ExifRead or
the core TIFF/EXIF fallback receives any bytes.

## Fix

`KodiFileAdapter.read()` now prefers Kodi's binary `readBytes()` API and converts
the returned bytearray to ordinary `bytes`. Seek/tell/size semantics stay unchanged,
so ExifRead and the bounded JPEG/EXIF recovery code continue to share one VFS-safe
file-like abstraction. A compatibility path remains only for test/legacy shims that
do not expose `readBytes()`.

The change is read-only and does not modify source media, scanning concurrency,
database schema or Query Model semantics. It also does not silently rewrite old
catalogue rows. Use **Metadata diagnostics** on a representative picture first; if
Fresh extraction now sees Camera/GPS metadata, run **Refresh metadata** for that
picture or a deliberately bounded folder refresh.
