# 0.3.5 home artwork performance and maintenance

Kodi's log showed that the automatic date refresh completed and immediately
reloaded the complete Estuary fork. Shortly afterwards Kodi failed to read and
recreate several local thumbnail-cache PNG files. The catalogue query itself
was not taking minutes; Kodi was rebuilding artwork from original SMB files,
including RAW pictures and video frames, while every home row had been
invalidated.

Version 0.3.5 reduces that work in four layers:

1. bundled home URLs carry `home=1` and use a separate default of ten items;
2. each picture row queries a bounded candidate pool and places common still
   formats before RAW/HEIF and video artwork;
3. the skin reads the plug-in's single `thumb` art key directly, and the plug-in
   supplies Kodi's canonical `image://` cache URI;
4. the daily service refresh uses `Container.Refresh` instead of `ReloadSkin`.

The first view after installing the new skin can still require Kodi to create
new local texture-cache entries, and a NEF that remains in a visible slot still
needs the RAW decoder. Subsequent views should reuse the cache. The exact gain
depends on SMB latency, file size and the Kodi texture cache, so real-device
validation remains part of release acceptance.

The maintenance portion adopts `InfoTagPicture` for fields it supports, guards
player filename lookups with `Player.HasMedia`, records directory or metadata
operations taking five seconds or more, and updates the no-Python QNAP patch
workflow. No database migration or rescan is required.
