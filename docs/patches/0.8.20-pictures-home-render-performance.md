# 0.8.20 Pictures Home render performance

The MyPicsDB Estuary Home integration has kept nine generic Pictures slots
materialized since 0.8.8 so Kodi can load `Home.xml` before the MyPicsDB service
publishes session-local Home properties. That architecture fixed a cold-start
race, but the skin subsequently resolved the persistent `home_row_N` add-on
setting throughout runtime visibility and row-label variables. Across nine
slots the two generated fragments contained 171 `Addon.SettingStr` references.

0.8.20 keeps all nine generic controls materialized and changes only their
runtime state source. The service already publishes `MyPicsDB3.HomeRow1` through
`MyPicsDB3.HomeRow9` after its abortable startup delay and whenever settings are
refreshed. The skin now compares those `Window(Home).Property(...)` values for
visibility, headings, random-generation selection and `browse=never` decisions.
Because the properties are used only by runtime `<visible>`/variable conditions
and never by an include-time condition, an initially empty property cannot
permanently omit a control; the row becomes visible when the service publishes
state.

This is intentionally a rendering-path optimization, not a scanner or provider
query change. Widget item limits, image URIs, database queries, provider
generations, random selection and scan scheduling are unchanged. The generated
Estuary patch revision advances to Omega 22 and Piers 20. Database schema stays
at 9 and Query Model stays at 1.
